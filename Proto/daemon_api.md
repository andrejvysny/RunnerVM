# daemon protocol v1 — runnerctl ⇄ runnerd over `runnerd.sock`

All methods `readOnly` unless marked. Long-running mutations return `{operationId}`; poll `operation.get`.

`instance.list`, `instance.get {id}`, `instance.create {profile, purpose?, ttlMs?, imageOverride?}` (mut, debug), `instance.stop {id, force}` (mut), `instance.delete {id}` (mut), `instance.taint {id, reason}` (mut), `instance.exec {id, argv, timeoutMs}` (stream), `instance.sshInfo {id}`, `instance.metrics {id}`, `instance.selfTest {id}`
`instance.create`'s three optional fields are the maintenance-instance surface. `purpose` is `runner` (the default, and what an older client that omits the field means) or `maintenance`: a maintenance instance is **pinned** — the scheduler never counts it as demand, never cancels it as surplus, never reaps it on `idleTTL`, never recycles it when tainted or retired, and never hands it a runner session — so scale-to-zero cannot take it away and only its ttl ever does. It still holds real cpu/memory/disk (and, on macOS, a guest slot) against the host budget, so admission refuses the runner VM that no longer fits behind it and the profile's advertised `X-ScaleSetMaxCapacity` shrinks while it runs. `ttlMs` is mandatory with `purpose: maintenance` (`MAINTENANCE_TTL_REQUIRED`) and must be 10s…24h (`MAINTENANCE_TTL_INVALID`); `pinnedUntil` is stamped as `now + ttlMs` and a reconcile step deletes the instance through the ordinary `instance.delete` path once it passes, logging `instance.maintenanceExpired` to `logs/events.jsonl`. `imageOverride` boots any image reference — digest, local name or registry reference — instead of the profile's, and is refused on a runner create with `IMAGE_OVERRIDE_MAINTENANCE_ONLY`; it is resolved, pulled and pinned exactly as a profile reference would be, and every admission check (guest OS, macOS platform floors and disk contract, runner freshness) grades the overridden image. Host mode is not special-cased: a draining or offline host refuses a maintenance create exactly as it refuses a runner one. `InstanceInfoDTO` reports `purpose` and `pinnedUntil` (both optional — a daemon predating the fields omits them and means `runner`).

`instance.selfTest` relays `agent.selfTest` to the instance's guest agent the way `instance.metrics` relays `agent.getMetrics`, and answers the guest's `{checks:[{name, ok, detail}]}` verbatim — no host-side grading. It needs a completed agent handshake, is read-only inside the guest and is safe while a job runs. A Linux guest has nothing to test and answers `{checks: []}`, which is a pass; `runnerctl vm self-test <id>` prints one ✓/✗ row per check and exits 1 if any failed.

`runner.list`, `runner.get {sessionId}` · `scaleset.list` · `operation.get {id}`, `operation.list` (`OperationInfo.result?` is a flat string map a finished operation reports, e.g. `pushedReference` on `push-image`: the immutable `@sha256:` reference the registry assigned) · `logs.tail {component?, instanceId?, lines}` (stream) · `metrics.snapshot`
`auth.status`, `auth.login {token}` (mut), `auth.logout` (mut) · `github.test` · `debug.runJit {profile}` (mut, debug) · `debug.demandSet {profile, assignedJobs}` (mut, debug) · `debug.scaleSetReconnect {profile}` (mut, debug)

`scaleset.list` returns one row per enabled profile: `{profile, name, githubScaleSetId, state, sessionState, sessionGeneration, lastMessageId, advertisedCapacity, assignedJobs, healthy, statistics, updatedAt, lastError}`. `name` is `runnervm-<profile>` (spec §14); `lastMessageId` is the message-queue cursor inside `sessionGeneration`; `advertisedCapacity` is what the next poll sends as `X-ScaleSetMaxCapacity` and is 0 while the host is draining. The message-session bearer token is never returned, logged, or persisted.

`debug.demandSet` overrides local demand and is rejected with `DEMAND_NOT_MANUAL` unless runnerd runs the manual demand provider (`RUNNERVM_DEMAND_MODE=manual`). With a scale set in front, demand is GitHub's statistics and nothing else.

`debug.scaleSetReconnect` closes the profile's current scale-set message session (the long poll) and forces the daemon to re-establish it, which always lands on a new `sessionGeneration` and `lastMessageId: 0` — the same recovery path an unexpected connection drop or a daemon restart takes (spec §45, §49). It is rejected with `DEMAND_NOT_SCALE_SET` unless the profile's demand comes from a registered GitHub scale set (`github.demand: scaleSet`, the default); a profile whose scale set has not finished registering yet answers `SCALE_SET_NOT_REGISTERED`. `scaleset.list` shows the new session and generation once the reconnect lands; nothing already queued or acquired is lost — the durable inbox (`scaleset.list`'s `lastMessageId`, spec §49) replays exactly as it would after a crash.

`image.pull` resolves the tag to a digest inside the call — so an unreachable registry, a rejected credential or a missing repository comes back as `REGISTRY_AUTH` / `REGISTRY_NOT_FOUND` right there — and then returns `{reference, manifestDigest, operationId, alreadyPresent, digest?}` without waiting for the transfer. `reference` is the immutable `<registry>/<repository>@sha256:…` (spec §21); `alreadyPresent` means the digest was already in the store and nothing was started. Concurrent pulls that resolve to the same manifest digest share one transfer and one `pull-image` operation (spec §137). `image.push` behaves the same way and answers `{reference, digest, operationId}`. Follow either with `operation.get`; `runnerctl image pull|push` does that by default and takes `--no-wait` to skip it.

`image.import`'s `hardwareModel` is macOS-only: base64 of `VZMacHardwareModel.dataRepresentation` (a tart `config.json` carries it under the same name). It only fills a gap — a sealed `metadata.json` that already declares `macos.hardwareModel` wins — and `runnerctl image import` refuses it with `--os linux` or when the value is not base64.

`image.inspectRemote` reads only the manifest and the two config blobs — no disk transfer, no row, no staging directory, nothing written — and answers `{reference, manifestDigest, os, architecture, format, virtualSizeBytes, transferBytes, runnerVersion?, runnerVersionHealth, guestAgent, docker, ssh, createdAt, minimumCPUCount?, minimumMemoryBytes?}`. It exists so a profile can be sized before the image is on the host: a macOS profile's `resources.disk` must equal `virtualSizeBytes` exactly and a Linux one's must be at least it. Unlike `instance.create`, an agentless image is described rather than refused — `guestAgent: false` is the answer, not an error. The tag → digest resolution it performs seeds the same cache `image.pull` reads.

`image.list` reports `canonicalReference` (the immutable reference this host resolved the image from) alongside `name` (the local label from the image manifest, which a later pull cannot move) and `pulledAt`. `system.status` reports `images.pulling`, the number of image rows with a transfer in flight.

Profile `image:` values may name a registry. The first `instance.create` after a profile change resolves the tag and pulls, so it is as slow as the image is large; the resolved digest is cached for five minutes per reference and every instance records the digest, never the tag.

`image.build` starts an in-daemon build from a `Runnerfile`-style recipe (see [docs/image-build.md](../docs/image-build.md)) and returns `{buildId, operationId?, name?, from, totalSteps}` without waiting for it to finish; `operationId` is `nil` only when nothing needed starting, which should not happen for a fresh build. Follow with `operation.get`, `build.get {buildId}` for a snapshot (`BuildInfoDTO`: `buildId, name?, state, operationId?, pushReference?, pushOperationId?, recipePath, recipeSHA256, contextPath, contextSHA256?, fromKind, fromReference, baseDigest?, baseSHA256?, cpuCount, memoryBytes, diskBytes, diskReservationBytes, timeoutMs, buildPath, logPath, workerPid?, totalSteps, currentStep, currentInstruction?, imageDigest?, failureCode?, failureMessage?, createdAt, startedAt?, finishedAt?, recoverySince?, updatedAt`; `recoverySince` is set only while restart recovery cannot prove the build's builder VM dead -- the build still holds its host capacity, base-image pin and directory until it can, or until the recovery deadline abandons the row with `BUILD_RECOVERY_ABANDONED`; it is absent on daemons predating schema v3; `args?` is the resolved `ARG` map the build ran with — build arguments are not secrets, the same map is in the image provenance and any pushed OCI config, and `image.build` refuses a value that looks like a credential with `BUILD_ARG_LOOKS_LIKE_SECRET`; `kind?` is `runnerfile` or `macosProvision` and is absent on daemons predating schema v4, where every build is a Runnerfile build; `managedName?` and `sourceDigest?` are set only on a `macosProvision` build and name the `images.managed[]` entry it is producing and the upstream manifest digest it is qualifying — a `macosProvision` build has no Runnerfile, so its `recipePath`/`recipeSHA256` are the provisioning script it shells out to and its `totalSteps` is 0), `build.list` for `{builds: [BuildInfoDTO]}`, or `build.log` to tail `build.log` (returns `{data, nextOffset, done}`; each call returns up to `maxBytes`, capped at 256KiB, plus `nextOffset` to resume from and `done` once the build is terminal and every byte has been returned). `build.cancel` returns `{buildId, state}`, is idempotent, and reports the build's state afterward; requesting it against an already-terminal build answers `BUILD_NOT_CANCELLABLE` rather than silently succeeding, and cancelling a build this daemon does not own whose builder worker cannot be proven dead answers `BUILD_WORKER_UNVERIFIABLE` with nothing released rather than freeing capacity a live VM is still using. `runnerd` answers all five with `BUILD_UNAVAILABLE` only when no `ImageBuildService` is wired in (the M1-M5 test harness); a production daemon always has one.

The `image.update.*` family drives `images.updates` (phase D6, `docs/design/distribution.md` "Update invariants"). A **track** is one `managed_images` row: either a registry tag an applied profile names (`kind: registryTag`, `name` *is* the canonical `<registry>/<repository>:<tag>`) or an `images.managed[]` entry (`kind: macosTart`, `name` is the local alias). A profile pinned to an explicit `@sha256:…`, and a bare local image name, are never tracked — there is nothing upstream to re-resolve. Track rows are (re)derived on every `config.apply`, whether or not `images.updates.enabled` is set; a row whose source has left the configuration is skipped, never deleted, because it still describes pins and retained digests on this disk.

All three methods answer `{tracks: [ImageUpdateTrackDTO]}`, where a track is `{name, kind, sourceReference, lastSourceDigest?, currentImageDigest?, candidateImageDigest?, state, lastCheckedAt?, lastUpdatedAt?, lastError?, autoUpdate}`. `state` is `ManagedImageState`: `idle`, `checking`, `downloading`, `building`, `qualifying`, `promoting`, `failed` — `idle` and `failed` are the only resting states. `lastSourceDigest` is the *upstream manifest* digest, `currentImageDigest`/`candidateImageDigest` are *local content* digests, and the two are never comparable. For **both** kinds `lastSourceDigest` is written at promotion and nowhere else, so it always names the upstream manifest the promoted image came from; recording it on a check instead would make the next sweep believe a move it never acted on had already been handled. A `macosTart` track additionally moves through `building` (phase D7): its upstream Tart export is not runnable, so its candidate is produced by a local `image_builds` row of `kind = macosProvision` — pull the export under `ImagePullPurpose.provisioningBase`, clone it into a builder VM, drive `scripts/provision-macos-tart.sh --attach` over SSH, seal, then cold-boot-qualify a clone of what was sealed (agent ready, `sw_vers`, `agent.selfTest`, SSH proven closed). Promotion for that kind also moves the local `image_aliases` row named by `images.managed[].name`, which is what a macOS profile's `image:` resolves through; a daemon with no image builder wired in reports `last_error` and promotes nothing.

`image.update.check` runs a resolve-only pass — one manifest plus two config blobs per track, bypassing the five-minute tag cache `image.pull` reads, and nothing is transferred, written or promoted. `image.update.run` starts a full resolve → pull → qualify → promote cycle and returns the pre-cycle snapshots immediately, the way `image.pull` answers before the transfer; poll `image.update.status`. Both take an optional `managed` naming one track and answer `MANAGED_IMAGE_NOT_FOUND` for a name this host does not track; both answer `IMAGE_UPDATES_UNAVAILABLE` on a daemon with no update service wired in (the M1-M5 test harness). `image.update.status` reads `managed_images` directly and therefore answers on such a daemon too. A track with `autoUpdate: false` is skipped by the scheduled sweep but still runs when asked for explicitly.

Qualification refuses a candidate that carries no guest agent (`IMAGE_NO_GUEST_AGENT`), whose `os` disagrees with the profiles using the reference (`IMAGE_INCOMPATIBLE_GUEST_OS`, or `MANAGED_IMAGE_MIXED_GUEST_OS` when two profiles disagree with each other), or whose baked-in runner is `tooOld` (`IMAGE_RUNNER_TOO_OLD`); with `images.updates.smokeTest` it additionally boots the candidate as a pinned maintenance instance and requires it to reach `idle` before promoting (`MANAGED_IMAGE_QUALIFICATION_FAILED` otherwise). Every one of those leaves `currentImageDigest` exactly where it was and records the reason in `lastError`; the next cycle retries. Promotion is a single row write — from that instant every `instance.create` resolving the tracked reference gets the new digest with no registry round trip — followed by retiring reusable VMs still on the superseded digest (spec §138) and by retention: digests past `images.updates.keepPrevious` are unpinned and deleted only where `image.delete`'s own pin/instance check agrees, and are otherwise left for a later `image.prune`.

`system.status.updates?: [ImageUpdateTrackDTO]` carries the same rows, optional for wire compat exactly like `builds` — a daemon predating the update service omits it and `runnerctl status` drops the `Updates` block rather than printing an empty heading. `runnerctl image update check|run|status` renders the track table; `run --wait` (the default) polls until every track is `idle` or `failed` and exits 1 if any failed.

`registry.login` is the second method that carries a secret, and the daemon owns the item: it writes `kSecClassInternetPassword` keyed by registry host, which is what runnerd's own pulls read. The password is never echoed back, logged or returned by `registry.status`. `registry.status` is offline — it reports which provider (`environment`, `dockerConfig`, `keychain`) would answer for every registry the profiles name, and the username it carries; it never contacts a registry. `runnerctl registry login --local` bypasses the daemon and writes the invoking user's Keychain instead, which only helps when runnerd runs as that same user.

`auth.login` carries the GitHub token. It travels over `runnerd.sock` (peer-UID checked, 0700 directory) and is written straight to `github.auth.source`; it is never echoed back, logged, or written to the applied YAML.

`runnerctl` never opens SQLite, instance files, or GitHub directly. Output modes: human table, `--output json`.

`system.drain`, `system.resume` and `system.offline` move `hosts.mode` (spec §109) with a compare-and-swap and an `audit_events` row, and all three answer `{mode, activeSessions, drained}`. `draining` advertises 0 capacity to every scale set and admits no new work while the jobs already on the host finish; `resume` returns to `normal` from either `draining` or `offline`; `offline` drains first when the host was still `normal`, because `normal -> offline` is not an edge. `system.drain {wait: true}` blocks until `activeSessions` reaches 0 or `timeoutMs` elapses and reports which happened in `drained`. `system.shutdown` drains, waits for the active sessions unless `force` (otherwise it fails `UNAVAILABLE`), answers `{accepted, mode, activeSessions}` and only then closes the socket; vmworkers and their VMs are deliberately left running for the next start to reconnect (spec §108).

`metrics.snapshot {format?}` returns `{collectedAt, families[], prometheus?}`, where each family is `{name, type, help, samples[]}` and each sample is `{labels[], value?, histogram?}`; `format: prometheus` additionally renders the 0.0.4 exposition text daemon-side so `runnerctl metrics --format prometheus` reproduces a scrape without the endpoint being enabled. Metric label values are profile names, instance ids, instance/session state names and fixed enumerations only — never anything a workflow supplied. The optional endpoint (`metrics.prometheus.enabled`, spec §43) serves `GET /metrics` and `GET /healthz` on loopback only; a non-loopback `listen` is rejected at startup with `CONFIG_VALIDATION_FAILED`.

`system.status` reports `daemon.mode` plus `daemon.activeSessions`, which is what `runnerctl status` prints as `Mode: draining (N active jobs)`.

`system.status.builds?: {running, queued}` counts non-terminal `image_builds` rows (`queued` is exactly `ImageBuildState.queued`; `running` is every other non-terminal state: `resolving`, `staging`, `booting`, `provisioning`, `sealing`). Optional for wire compat — a daemon predating the image builder simply omits the field, and `runnerctl status` drops the `Builds:` line entirely rather than printing zeroes it cannot back up. A build counts as active work for `system.drain`/`system.shutdown` exactly like a running instance (`HostModeControl.activeWork()`).
